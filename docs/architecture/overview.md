## 1. 系统定位

三省六部 · Edict 是一个**制度化的 AI 多 Agent 协作平台**。

核心理念：用 1300 年前的帝国官僚制度（三省六部）来设计 AI 多 Agent 协作架构，实现**分权制衡 + 完全可观测 + 实时可干预**。

与传统框架的核心差异：

| 维度 | CrewAI / AutoGen | **三省六部** |
|------|-----------------|-------------|
| 协作模式 | 自由讨论 / Human-in-loop | 制度化协作（权限矩阵 + 状态机） |
| 质量保障 | 依赖 Agent 智能 | 门下省专职审核 · 可封驳 |
| 可观测性 | 低 | 极高（完整活动流） |
| 可干预性 | 无 / 需人工批准 | 一键 stop / cancel / advance |
| 失败恢复 | 重新开始 | 自动重试 → 升级 → 回滚 |

## 4. 状态机

### 状态流转

```
皇上下旨 → Pending → Taizi → Zhongshu → Menxia → Assigned → Doing → Review → Done
                                  ↑          │
                                  └── 封驳 ──┘
                                                          Blocked (叫停)
                                                          Cancelled (取消)
```

### 状态定义

| 状态 | 含义 | 负责部门 | 对应 Agent |
|------|------|---------|-----------|
| `Pending` | 待处理 | 皇上 | `zhongshu` |
| `Taizi` | 太子分拣中 | 太子 | `taizi` |
| `Zhongshu` | 中书规划中 | 中书省 | `zhongshu` |
| `Menxia` | 门下审议中 | 门下省 | `menxia` |
| `Assigned` | 尚书派发中 | 尚书省 | `shangshu` |
| `Doing` | 六部执行中 | 六部 | 从 `org` 推断 |
| `Next` | 待执行 | 六部 | 从 `org` 推断 |
| `Review` | 汇总审查中 | 尚书省 | `shangshu` |
| `Done` | 已完成 | — | — |
| `Cancelled` | 已取消 | — | — |
| `Blocked` | 已叫停 | — | — |

## 5. 制度保障机制

| 保障机制 | 实现方式 | 防护效果 |
|---------|---------|---------|
| **制度性审核** | 门下省必审议所有中书方案，不可跳过 | 防止 Agent 胡乱执行 |
| **分权制衡** | 权限矩阵：谁能调谁严格定义 | 防止越权操作 |
| **完全可观测** | 看板多面板 + 完整活动流 | 实时掌握任务全局 |
| **实时可干预** | 一键 stop / cancel / resume / advance | 紧急纠正 |
| **自动容错** | 停滞检测 → 自动重试 → 升级协调 → 自动回滚 | 无人值守恢复 |

## 8. 三层代码架构

```
edict/
├── backend/         后端服务（API · Worker · ORM · 迁移）
├── kernel/          工作流内核（状态机 · 引擎 · 端口 · 适配器）
├── flutter_app/     Flutter Web 主前端（维护中）
├── frontend/        React 看板前端（归档）
├── agents/          12 个 Agent 的 SOUL 配置
├── tests/           仓库级测试
├── scripts/         运维脚本
└── docs/            文档
```

- **`kernel/`**：可安装 Python 包，包含状态机、工作流引擎和抽象端口定义
- **`backend/`**：应用层，通过适配器对接 kernel 的端口到 PostgreSQL / Redis / OpenClaw
- **`flutter_app/`**：Flutter Web 主看板，通过 HTTP / WebSocket 调用 backend
- **`frontend/`**：React 旧版看板，已归档，不再作为主线维护目标

> 专题文档：[代码结构说明](code-structure.md) 详细解释三层协作关系。

## 9. 核心数据流

### 任务创建 → 完成的主数据流

```
用户下旨 (Feishu/Telegram/看板)
  │
  ▼
POST /api/create-task  →  数据库创建任务  →  事件总线发布
  │
  ▼
orchestrator_worker 消费事件
  │
  ▼
dispatch_worker 调用 OpenClaw Agent
  │
  ▼
Agent 执行 → kanban_update.py 上报进展/状态
  │
  ▼
状态机迁移 → 触发下一个 Agent 派发
  │
  ▼
... (三省流转) ...
  │
  ▼
Done → 奏折归档 → 飞书/Telegram 回报皇上
```

### 活动流数据源

| 数据源 | 内容 | 来源 |
|--------|------|------|
| `flow_log` | 状态转移记录 | Agent 通过 `kanban_update.py flow` 上报 |
| `progress_log` | Agent 实时工作汇报 | Agent 通过 `kanban_update.py progress` 上报 |
| Session JSONL | Agent 思考过程、工具调用 | OpenClaw 框架自动记录 |

三层数据在 `get_task_activity()` 中融合为统一活动流，供看板渲染。

## 10. 调度系统

每 60 秒执行一次 `handle_scheduler_scan()`，处理停滞任务：

```
停滞检测（超过阈值无新进展）
  │
  ├─ 阶段 1：自动重试（retryCount < maxRetry）
  │     └─ 重新派发当前状态的 Agent
  │
  ├─ 阶段 2：升级协调（escalationLevel < 2）
  │     ├─ L1 → 唤醒门下省介入
  │     └─ L2 → 唤醒尚书省介入
  │
  └─ 阶段 3：自动回滚（escalationLevel >= 2）
        └─ 恢复到快照状态，重新派发
```

> 专题文档：[任务分发流转架构 §2.4](task-dispatch-architecture.md#24-调度系统超时重试停滞升级自动回滚) 包含完整调度算法与故障恢复场景。
